# Grade comparison investigation

## Evidence

- The [official BilimClass mobile guide](https://help.bilimland.kz/l_rus/knowledge_base/item/356645) describes lesson grades, subject history and predicted grades. It does not document grade comparison, its data source or its calculation.
- MaterialClass currently opens a placeholder from `GradeTile` in `app/src/main/java/org/materialclass/ui/GradesScreens.kt`. It states that classmates' grades are unavailable and makes no comparison request.
- The existing grade pipeline combines the subjects response with the current student's journal records by schedule UUID. The journal request is scoped to the current user and student groups. It does not establish an API contract for classmates' grades or aggregate comparison statistics.
- Static string inventory of the user-supplied BilimClass APK set, SHA-256 `d995f8fc400825776f2a19ec301b21e1c7ea9f16cc56a96cc14f9694737a1e20`, identifies an ARM64 Flutter `libapp.so` containing `api/mobile/comparison/classroom/lesson`, `fetchComparisonInfo`, `ComparisonRepository`, `ComparisonInfo`, `StudentMark`, `ClassmatesMark` and `_ComparisonDiagram`. The archive identifies package `com.bilimland.bilimclass` and version code 117. These are literal strings, not observed network traffic or reconstructed call sites.
- An authorized read-only probe using one student account and a web-login access token returned HTTP 422 JSON for `GET https://api.bilimclass.kz/api/mobile/comparison/classroom/lesson` without query parameters. The response had root keys `errors` and `message`; the validation errors named both `uuid` and `type` as required. A prior sanitized probe on 2026-11-13 independently recorded the same host, method and status. This confirms only a validation response in those contexts, not that the APK uses this host, token, method, or query structure.
- ARM64 Dart AOT snapshot reconstruction provides stronger evidence than the string inventory. In `ComparisonRepository.fetchComparisonInfo` at `libapp.so` virtual address `0x5a6e10`, the pool entries resolve to base URI `https://api.bilimclass.kz/` and path `api/mobile/comparison/classroom/lesson`. The function builds a map with keys `uuid` and `type`, passes it as `queryParameters` to the URI, and calls the HTTP client's `get` method at `0x78dd40`. Their values come from repository instance fields at offsets `0xb` and `0xf`; their upstream meaning and possible values are not yet established. The client and authorization headers are not established by this call site.
- The same function returns null for HTTP 404; otherwise it decodes the response body as JSON and calls `ComparisonInfo.fromJson` at `0x5a6f7c`. That constructor reads `maxScore`, `studentMark`, and `otherMarks`. The nested `StudentMark.fromJson` at `0x5a7188` reads `score` and `grade`; `ClassmatesMark.fromJson` at `0x5a72d4` reads `score`, `count`, and `grade`. These are fields consumed by the APK, not an observed complete response or a guarantee that all fields are required. Error behavior for other HTTP statuses remains unverified.
- On 2026-11-15, authorized read-only requests with a web-login bearer token and school header used the schedule UUID of a lesson with an actual mark, obtained from the current student's journal. Each of `type=sor`, `type=soch`, and `type=formattedScore` returned HTTP 200 for a corresponding marked lesson. In each response `maxScore` was an integer; `studentMark` contained integer `score` and string `grade`; `otherMarks` was an array of objects containing integer `count`, integer `score`, and string `grade`. The observed array lengths were 5, 11, and 2 respectively. No personal identifiers, grades or tokens were recorded. This demonstrates these values for this account and those lessons, not exhaustive enum values, data ranges, authorization rules or nullability.
- A different existing schedule UUID returned HTTP 200 for each of those three types with `maxScore: null`, `studentMark: {score: null, grade: null}`, and `otherMarks: []`; the journal state for this lesson was not checked. A synthetic all-zero UUID with those types returned HTTP 404. With that same synthetic UUID, `intermediate`, `unsupported`, and `invalid` returned HTTP 422 with a `type` validation error. The APK's `RegularMarkTypeV2` enum contains all five values `sor`, `soch`, `formattedScore`, `intermediate`, and `unsupported`, but the latter two were rejected by this tested endpoint.
- The supplied prototype's `components.js` shows a ten-row distribution and a highlighted own grade, but derives it from generated preview data and replaces zero counts with one. This is a design mock, not evidence of the upstream calculation or API.

## Unknowns and next steps

The tested `uuid` values were schedule UUIDs, and the three type values above produced successful responses with matching marked lessons. It is not established whether other identifiers or type values are also accepted. The observed access token was from the web login; the APK's exact headers, cross-role access rules, complete error handling, field ranges and server aggregation rules remain unverified. Do not treat empty arrays as fabricated scores, or extrapolate one account's observations to other schools or roles.
