## Open verification gates

CI prints the resolved build, debug runtime, unit-test and instrumented-test dependency trees and checks the merged debug manifest. These reports are evidence for a subsequent artifact-by-artifact review, not an SPDX license inventory or checksum verification. Android manifest merging detects conflicting minimum SDK requirements for the graph used by that build, but a successful merge does not establish the requirements of future dependencies or storage APIs. The API 24 emulator tests the current launcher only.

Before release, inventory every resolved artifact and its published license metadata, including build and test tools separately from shipped runtime dependencies. Confirm SPDX identifiers, GPL-3.0 compatibility and required license texts and NOTICE attribution for each shipped component, then retain the complete inventory and corresponding source references. Apache-2.0 is compatible with GPLv3 subject to its conditions, not a blanket finding for the entire graph: [ASF compatibility](https://www.apache.org/licenses/GPL-compatibility.html). Treat missing metadata or incompatible terms as blockers.

The dependency versions in the catalog and wrapper distribution checksum do not lock the transitive graph or authenticate each downloaded dependency. Generate and review Gradle dependency locks and verification metadata from independently authenticated sources before trusting them; do not accept checksums generated from the same unverified downloads as independent evidence. GitHub action tags were resolved to full commit SHAs, but their transitive downloads, runner images, JDK patch releases and Android SDK packages remain outside that pinning.

Stage 3 must separately select and review storage and Keystore mechanisms, API requirements, atomicity and backup behavior. API 23 Keystore AES/GCM availability is only a candidate input, not a selected or validated storage implementation: [KeyGenParameterSpec](https://developer.android.com/reference/android/security/keystore/KeyGenParameterSpec). Re-evaluate minSdk against the complete resolved manifests and the selected storage implementation; do not infer a final floor from this scaffold. Device backup, dynamic color, `java.time` on API 24-25 and target SDK behavior remain separate gates.
